# Ruseact Example typography policy

Typography is the highest-priority anti-slop review area. The values below are
proposed project defaults, informed by system guidance and owner requirements;
they are not universal laws. A valid exception documents the user need,
accessibility rationale, established branding, or technical-data constraint.

## Defaults

| Semantic role | Default size | Default weight | Guidance |
|---|---:|---:|---|
| Body | 15–16px | 400 | Use readable measure and about 1.5 line-height for long text. |
| Labels | 13–14px | 400–500 | Sentence case; do not use tracking as a substitute for hierarchy. |
| Buttons | 14px | 500 | State and action must remain clear without boldness. |
| Section heading | 18–20px | 500–600 | Use a real heading and place it near its content. |
| Page heading | 26–32px | 500–600 | Scale to task; do not manufacture hierarchy with size alone. |
| Secondary metadata | 12–13px | 400 | Keep it readable and non-functional. |

## Required defaults

- Sentence case for headings, labels, buttons, navigation, and ordinary copy.
- Regular body text; regular or medium functional labels and buttons.
- Deliberate, restrained heading emphasis.
- Avoid unnecessary 700–900 weights, bold paragraphs, arbitrary bold words in
  headings, repeated eyebrow labels, decorative numbered markers, excessive
  uppercase, tracked uppercase micro-labels, excessive negative tracking,
  tiny low-contrast controls, and monospace for ordinary prose/navigation.
- Use a documented semantic type scale and heading hierarchy.
- Do not flag legitimate acronyms, code, identifiers, version strings, or
  protocol names as casing slop.

## Evidence and exceptions

IBM guidance supports hierarchy, consistency, leading, tracking, alignment, and
case review. USWDS guidance recommends readable measures and leading and warns
against long all-caps or long bold/italic passages. Fluent guidance recommends
semantic ramps and familiar system fonts. These sources guide review; they do
not define a single correct font or size.

An exception record should state: role, value, purpose, affected content,
accessibility check, and why a less emphatic treatment would fail.
