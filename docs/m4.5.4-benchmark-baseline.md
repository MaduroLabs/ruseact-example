# M4.5.4 Application Benchmark Baseline

## Purpose and scope

This is a pre-M5 application-level baseline for the installed Ruseact alpha.1
consumer. It is not a competitive framework benchmark and it does not compare
Ruseact with React. It measures real production consumer modules in Chromium,
with correctness checked after each operation.

The durable raw evidence is
[`docs/evidence/m4.5.4-benchmark-results.json`](evidence/m4.5.4-benchmark-results.json).
The generated working output is under ignored `target/consumer-audit/`.

## Measurement boundaries

Initial-mount workloads measure from the benchmark page module's start marker
to successful application mount. They exclude network fetch and browser paint.
Operation workloads measure the application operation, signal writes, the
documented explicit flush calls, and correctness observation. Setup/reset work
is outside the timed region wherever the harness can separate it.

The harness records operation count, flush count, correctness, raw samples,
median, IQR, and dispersion ratio. A non-positive or non-finite sample is not
accepted as a valid measurement. `performance.now()` quantization can therefore
leave a workload unresolved rather than silently turning a zero duration into a
baseline.

## Workloads

Counter:

- initial mount;
- one scalar update plus flush;
- repeated scalar updates;
- multiple writes before one flush;
- equality-preserving write.

Conditional:

- initial mount;
- selected branch mount;
- nested conditional activation.

Todo, at sizes 10 and 100:

- append;
- remove;
- toggle retained task;
- filter;
- reverse;
- edit retained title;
- clear completed.

Reorderable List, at sizes 10 and 100:

- append;
- prepend;
- remove;
- reverse;
- deterministic shuffle;
- no-op reconciliation;
- retained title update.

Each operation uses the existing public application test boundary. The harness
does not call DOM movement methods or bypass the renderer.

## Results: every independent execution

Each run produced 39 workload rows and 5 samples per row. Across all three
runs, 109 rows were valid, 2 rows were high variability, and 6 rows were
unresolved. The six unresolved rows are the two reorderable no-op workloads in
each run; their very fast samples quantized to zero or near-zero milliseconds.
Nineteen non-positive raw samples were retained as invalid evidence by the
validator. The unresolved rows are not counted as valid performance results.

| Run | Rows | Valid | High variability | Unresolved | Result |
| ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 39 | 37 | 0 | 2 | Completed with unresolved no-op rows |
| 2 | 39 | 36 | 1 | 2 | Completed with unresolved no-op rows; Todo remove variability |
| 3 | 39 | 36 | 1 | 2 | Completed with unresolved no-op rows; Todo append variability |

## Integrity assessment

`corepack pnpm audit:benchmark:validate` passed the report schema and confirmed:

- exactly three runs;
- 39 rows per run;
- positive finite samples required;
- correctness required;
- unresolved measurements retained rather than accepted;
- dispersion reported rather than silently accepted.

The no-op workload is a measurement-resolution limitation, not evidence of zero
cost. The equality-write row is reported as high variability in one run and is
not converted into a failure or hidden. No arbitrary retries or relaxed gates
were used.

## Reproduction

```sh
corepack pnpm audit:benchmark
corepack pnpm audit:benchmark:validate
```

The first command rebuilds the production consumer and runs three independent
Chromium executions. The second command rejects malformed or invalid reports.
The harness records the actual browser, package source, consumer commit,
configuration, raw samples, and correctness status.

## Limitations and M5 comparison method

The local host uses Node 22 rather than the repository's Node 24 pin, and this
baseline is local rather than a hosted-runner aggregate. Browser paint is not
measured, so durations must not be called INP or frame time. The small list
sizes and five-sample rows are suitable for a first baseline, not for broad
scaling claims. Future M5 comparisons should preserve the schema, operation
boundaries, correctness prerequisites, raw sample retention, and environment
metadata, and should report changed execution semantics separately from changed
application code.
