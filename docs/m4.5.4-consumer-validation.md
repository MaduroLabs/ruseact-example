# M4.5.4 Consumer Validation Report

## Executive summary

This audit validates the five independently installed Ruseact alpha.1 examples:
Hello World, Counter, Conditional Playground, Todo Application, and Reorderable
List. The reviewed consumer baseline is `3e072edd5996198dada68c437f7384aa7d10c732`.
The installed packages are the matching alpha.1 set built from promoted framework
commit `2a0ab7781b6c56fde643bf6bc8ed3f550097209c`.

The real Chromium suite passed for all five applications, including nested
conditional ownership, keyed retention, input state, explicit flushing, and
cleanup. The audit found no active alpha.1 correctness defect. The historical
alpha.0 duplicate-local-structural-ID failure is resolved by the promoted
owner-scoped registration fix and is covered by installed-package regression
testing.

The main pre-M5 friction is intentional manual execution: application code must
declare dependencies, publish JavaScript collections through scalar revisions,
and call `root.flush()` explicitly. Retained-data updates in Todo and the
reorderable list require a bounded second explicit flush because work generated
during the first snapshot is deferred. This is documented behavior, not an
automatic scheduling implementation.

The repository is technically suitable for a separately authorized static demo
deployment after a final deployment-hygiene review. Deployment was not
performed. In particular, the query-gated test and benchmark interfaces should
be isolated or removed from a public demo build before authorization.

## Ownership and cleanup findings

The consumer bootstrap in `src/bootstrap/mount.ts:72-236` verifies WASM and
runtime initialization, creates one root, and owns one application runtime. Its
disposal sequence is:

1. renderer root disposal;
2. application-owned signal cleanup;
3. runtime disposal.

If renderer cleanup fails, application-owned resources and the runtime are
retained. Original and cleanup failures are preserved in
`ApplicationLifecycleError`. Reentrant disposal is rejected, repeated disposal
after successful completion is safe, and persisted `pagehide` events do not
dispose a page that may return from the back-forward cache.

The browser suite verified detached renderer-owned listeners no longer invoke
managed callbacks, explicit application disposal removes managed DOM, and
repeated disposal does not remove unrelated DOM. Application code does not
dispose renderer-owned keyed item signals. Internal retention beyond these
observable boundaries is not measurable through public APIs.

At the framework source level, alpha.1's installed renderer uses a
`WeakMap<object, Map<string, StructuralRecord>>` in
`packages/ruseact-dom/src/bindings.ts:309-329` and reserves structural records
before initial evaluation at `:504-575`. Conditional and keyed registrations
pass the owning component scope (`renderer.ts:1063-1068` and `:1398-1402`).
This is the source-level explanation for the resolved alpha.0 nested-local-ID
failure; it is not a new consumer API.

## Accessibility and UX observations

`corepack pnpm audit:accessibility` performed a bounded heuristic check in
Chromium. All five pages contained a `main` landmark. Counter had 3/3 named
buttons; Conditional had 1/1 labeled form control and 1/1 named button; Todo
had 4/4 labeled controls and 12/12 named buttons; Reorderable had 9/9 labeled
controls and 35/35 named buttons. Counter and Conditional showed an explicit
3px solid focus outline; Todo and Reorderable used the browser's `auto` 1px
focus indicator in this probe.

This is not a WCAG audit. Recommended consumer follow-up is to standardize a
visible focus style across the form-heavy examples and manually review keyboard
order, error presentation, responsive layout, and empty states before any demo
deployment.

## Confirmed defects and intentional limitations

### Resolved correctness defect

The alpha.0 package set had a confirmed nested structural identity collision:
independent conditional regions could both use local ID `r0` and fail during
branch activation. The alpha.1 owner-scoped registration fix was verified in
installed-package browser execution and the Conditional Playground. It is not
an active alpha.1 defect.

### Intentional architectural limitations

- Signals support scalar values and explicit dependency declarations.
- Components execute one-shot setup with immutable initial props.
- `root.flush()` is explicit and one-pass; no automatic scheduler exists.
- Work generated during a flush can require a separate bounded flush.
- Filtered keyed items are structurally removed and later receive fresh
  activations.
- Runtime TSX compilation, HMR, React compatibility, hooks, and implicit
  dependency tracking are not part of alpha.1.

### Consumer/tooling friction

- Private packages require vendored matching tarballs and independent checksums.
- TSX source discovery and development watching are maintained by the consumer.
- The provisional JSX declaration is intentionally narrow in semantic intent,
  but its intrinsic-element index signature is broad for editor compatibility.
- Component-local mutable state and lifecycle callbacks are not available at the
  public consumer boundary.

## Deployment readiness

The production build emits relative multi-page HTML, JavaScript, CSS, and the
packaged WASM asset. `pnpm build` is deterministic with the committed vendored
artifacts and does not require framework source or an external CDN. A static
deployment could use `pnpm build` and publish `dist/`, with Node 24.22.3 and
pnpm 12.16.1 available through Corepack during the build.

This repository was not deployed. Before authorizing a public demo, remove or
isolate the query-gated `?test=1` browser interface and `?benchmark` mount
marker, confirm they are not reachable from normal navigation, and run a final
production asset inspection. The current CI has no deployment workflow and no
deployment credentials.

## M5 handoff

The highest-value research question is whether Ruseact should add an opt-in,
root-local scheduling coordinator while preserving explicit `flush()` as a
debuggable and compatible boundary. The proposal, alternatives, invariants,
and human decision records are in
[`docs/m5-scheduling-proposal.md`](m5-scheduling-proposal.md).
