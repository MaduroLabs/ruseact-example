# M4.5.4 Developer Experience Audit

## Executive summary

The alpha.1 consumer experience is viable for small experimental applications,
but it exposes the execution model directly. The strongest friction is not
package loading or DOM correctness; it is the amount of explicit coordination
required when JavaScript collections, scalar revisions, retained item fields,
and one-pass flushing meet.

The five examples demonstrate that the public contracts are expressive enough
for static output, scalar bindings, nested structural regions, keyed retained
items, filtering, and native range movement. The main future work should improve
execution ergonomics and diagnostics without hiding ownership, dependency, or
flush semantics before those invariants are formally reviewed.

## Methodology and evidence

The audit used the consumer baseline, installed alpha.1 tarballs, the real
Chromium harness, compiler probes, source inspection at framework commit
`2a0ab7781b6c56fde643bf6bc8ed3f550097209c`, and three independent benchmark
runs. Findings use E0–E4 evidence levels defined in
`docs/m4.5.4-consumer-validation.md`.

Authoring complexity was assessed by inspecting representative Counter, Todo,
and Reorderable List modules. Counts distinguish framework-required code from
application logic, test-only code, and build wrapper code; no single numeric
“DX score” is claimed. The benchmark measures synchronous JavaScript plus
renderer/WASM work inside `performance.now()` boundaries. It does not measure
network, paint, INP, or a competing framework.

## Authoring complexity measurements

| Representative task | Framework-required authoring observed | Main source of friction |
| --- | --- | --- |
| Counter scalar update | Signal creation, explicit binding dependency, structured results, explicit flush | Manual execution boundary |
| Todo collection update | JavaScript immutable publication, revision write, descriptor projection, field handles, bounded follow-up flush | Collection/revision discipline |
| Reorderable movement | JavaScript order publication, stable keys, revision write, one explicit flush | Keyed marker and immutable props |
| Conditional branch | Explicit selector dependency, boolean evaluator, lazy branch factories | Narrow compiler subset |

The required setup is visible and teachable, but it is more verbose than a
system with implicit tracking and automatic scheduling. That difference is an
architectural choice for alpha.1, not evidence that every extra line is
framework overhead.

## Manual flush findings

The installed DOM bindings source explicitly rejects reentrant flushes
(`packages/ruseact-dom/src/bindings.ts:602-609`), snapshots the pending records
before dispatch (`:614-638`), and skips exact computations disposed during the
same snapshot (`:645-652`). The public report deliberately exposes
`pendingAfter: "not-inspected"`; it is not a quiescence signal.

| Category | Consumer evidence | Flush behavior |
| --- | --- | --- |
| Scalar-only update | Counter increment/decrement | One explicit flush; no DOM change before it. |
| Structural-only update | Conditional branch activation and reorder movement | One explicit flush in tested paths. |
| Structural update generating retained scalar work | Todo toggle/save and retained title update | First flush reconciles structure and writes retained fields; a second bounded explicit flush exposes the field binding. |
| Multiple writes before one flush | Counter multiple-write probe | Writes are coalesced through the existing pending graph and one flush is measured. |
| Equality-preserving update | Counter equality probe | The write is reported unchanged; the application still uses the explicit boundary to keep the event contract simple. |
| Work generated during active flush | Todo/reorder retained fields | New work is deferred to the next snapshot; no recursive drain is used. |
| Reentrant execution | Framework source and negative/runtime contract | Reentrant `flush()` returns `reentrant_flush`. |

The current examples therefore use an explicit, bounded second flush only where
the measured retained-field path requires it. They do not use
`flush-until-empty`, microtasks, animation frames, or hidden scheduling.

## Collection reactivity

Todo and Reorderable List keep the authoritative collection in JavaScript. A
scalar revision signal invalidates the keyed structural computation. The
collection evaluator reads current application state, emits stable scalar item
field schemas, and uses stable monotonically increasing IDs as keys.

This prevents stale array captures and positional closures only through a
combination of compiler shape, runtime keyed semantics, and application
discipline. The runtime can reject duplicate keys and invalid result shapes, but
it cannot infer that an application forgot to publish a mutated JavaScript
array. The current approach is safe for the demonstrated scalar field model;
object/array signals and Proxy reactivity remain intentionally out of scope.

## Component and local-state findings

`defineComponent()` setup is one-shot and initial props are immutable. This is
effective for retained Todo and Reorderable items because renderer-owned scalar
field handles update bindings without rerunning item setup. It is less
convenient for draft text, expanded state, and resources that would naturally be
owned by a component instance.

The examples use application-owned selectors or branch-local conditional
regions instead of inventing a component-local state API. Removing a branch
disposes its branch-local DOM and listeners; reopening creates a fresh lifetime.
The public boundary has no general cleanup callback or owner registry, so the
consumer reports setup counts and externally observable listener/DOM behavior,
not fabricated disposal counters.

## JSX and TypeScript authoring

The installed compiler accepts the explicit marker subset. Dynamic JSX text
without `ruseact.bindText` is rejected with `implicit_dynamic_binding` and a
source location. A closure-shadowing probe produced two such diagnostics; the
safe workaround is to keep evaluator parameters explicitly named and wrap
dynamic values in supported markers.

The consumer declaration file provides provisional marker and intrinsic-element
types. Its broad intrinsic index signature improves authoring continuity but is
not a permanent structural type system. Compiler diagnostics remain
authoritative. Component placement and keyed item factories require occasional
casts because the installed compiler's public types are narrower than the
application's inferred closure shapes.

## Error handling and lifecycle

The public APIs return structured results with stable codes and operations.
This is more application glue than exception-only APIs, but it makes failures
traceable. The negative harness demonstrates actionable checksum, compiler,
signal, WASM, and root errors.

`mountApplication()` is consumer-local lifecycle glue. It owns the explicit
WASM initialization sequence and preserves fail-closed cleanup: renderer cleanup
must succeed before application-owned signals and runtime are released. This
contract is correct but requires the consumer to understand ownership order.

## Package distribution and build tooling

Private packages cannot be installed from npm. The matching vendored tarballs,
manifest, checksums, provenance, license, and pnpm override make installation
durable but add review work. A new example currently requires updates to the
TSX source list, generated module declarations when needed, dev watcher, Vite
HTML input list, index link, browser harness, and documentation. The explicit
list is easy to audit but does not scale as cleanly as a future consumer-local
discovery helper.

The build-time compiler is correctly absent from browser runtime assets. The
watcher offers bounded recompilation and full-page reload, not state-preserving
HMR. A small official bundler integration could reduce repeated consumer glue in
a future milestone, but is not implemented or implied here.

## Consolidated finding register

Severity uses **Blocker**, **High**, **Medium**, and **Low** for consumer impact;
it does not assign framework priority automatically.

### DX-001 — Explicit dependency and flush ceremony

- **Category / examples:** Execution ergonomics; Counter, Conditional, Todo,
  Reorderable.
- **Expected:** A state operation has an obvious completion boundary.
- **Actual:** The author declares dependencies, checks CoreResults, writes
  signals, and calls `root.flush()` explicitly.
- **Reproduction / evidence:** Counter and all application event helpers;
  E3/E4. Framework `bindings.ts:602-652`.
- **Impact / workaround:** Medium friction, not a correctness blocker; keep
  the boundary explicit and test no-update-before-flush behavior.
- **Constraint:** Preserve one-pass semantics and ownership.
- **Recommended action:** PROPOSE an opt-in scheduling layer only after M5
  decisions; complexity Medium; target M5.1–M5.3.

### DX-002 — Deferred retained-field work

- **Category / examples:** Execution semantics; Todo and Reorderable.
- **Expected:** One collection update makes retained scalar fields visible.
- **Actual:** Some structural updates write field signals after the current
  snapshot, requiring a bounded second flush.
- **Reproduction / evidence:** `todo.toggle-retained-*`, `todo.edit-retained-*`,
  and `reorderable.retained-title-*`; E3/E4.
- **Impact / workaround:** Medium friction, no blocker; call a second explicit
  flush only for these operations and document why.
- **Constraint:** No recursive queue drain.
- **Recommended action:** Add scheduler contract tests and a completion model;
  complexity High; target M5.1/M5.4.

### DX-003 — JavaScript collection plus revision signal

- **Category / examples:** Collection authoring; Todo and Reorderable.
- **Expected:** Mutating application data invalidates the view naturally.
- **Actual:** The application must publish a collection and increment a scalar
  revision; stale arrays and positional closures are unsafe.
- **Evidence:** E3; `src/examples/todo/` and `src/examples/reorderable/`.
- **Impact / workaround:** Medium friction, not a blocker; centralize model
  operations and use stable scalar descriptor fields.
- **Constraint:** Alpha.1 signals are scalar-only and explicit.
- **Recommended action:** Research a typed collection adapter separately from
  M5; complexity High; future consumer/runtime milestone.

### DX-004 — One-shot setup and no general component-local state

- **Category / examples:** Component authoring; Conditional, Todo, Reorderable.
- **Expected:** Draft and expanded state can be owned naturally by a component.
- **Actual:** Setup is one-shot, props are immutable, and no public cleanup hook
  or local-state API exists.
- **Evidence:** E1/E3; installed `defineComponent` contract and examples.
- **Impact / workaround:** Medium friction, not a blocker for these examples;
  use scalar handles, application selectors, or branch-local state.
- **Constraint:** Preserve one-shot semantics unless separately approved.
- **Recommended action:** Separate local-state/lifecycle research from M5;
  complexity High; later milestone.

### DX-005 — Provisional JSX typing

- **Category / examples:** TypeScript authoring; all TSX.
- **Expected:** Editor types precisely describe supported intrinsic elements and
  compiler markers.
- **Actual:** Consumer-local declarations are provisional and compiler support
  is narrower than normal JSX.
- **Evidence:** E2; `src/ruseact-compiler.d.ts`, negative compiler probes.
- **Impact / workaround:** Medium friction; rely on compiler diagnostics and
  keep declarations narrow in semantic intent.
- **Recommended action:** Improve declaration generation/typing independently;
  complexity Medium; post-M5 or tooling milestone.

### DX-006 — Consumer-maintained source discovery

- **Category / examples:** Build tooling; all examples.
- **Expected:** Adding an example requires only application source.
- **Actual:** `scripts/precompile.mjs`, `scripts/dev.mjs`, Vite inputs, index,
  test harness, and docs all need coordinated edits.
- **Evidence:** E1; actual M4.5.3.x changes.
- **Impact / workaround:** Low/Medium friction; use the documented checklist.
- **Recommended action:** Evaluate a consumer-local discovery helper or future
  Vite integration; complexity Medium; post-M5.

### DX-007 — Vendored private artifact process

- **Category / examples:** Distribution; all examples.
- **Expected:** A normal package install resolves the framework.
- **Actual:** Three matching tarballs and independent provenance/checksums are
  required because packages are unpublished.
- **Evidence:** E1/E2; `scripts/verify-artifacts.mjs`.
- **Impact / workaround:** Medium setup friction; run `artifacts:verify` and
  preserve the full set.
- **Recommended action:** Decide on a durable pre-publication distribution
  channel; complexity Medium; release/distribution milestone.

### DX-008 — Limited lifecycle observability

- **Category / examples:** Diagnostics; Conditional, Todo, Reorderable.
- **Expected:** Application code can observe all component disposal events.
- **Actual:** Public APIs expose setup and external DOM/listener behavior, not a
  general cleanup callback or owner registry.
- **Evidence:** E1/E3.
- **Impact / workaround:** Low for correctness, medium for education; avoid
  claiming internal disposal metrics.
- **Recommended action:** Human review before any diagnostic API; complexity
  Medium; later lifecycle milestone.

### DX-009 — Browser focus/selection variability

- **Category / examples:** Browser-specific behavior; Reorderable.
- **Expected:** Retained input focus follows native keyed movement.
- **Actual:** Chromium preserved focus when the focused item moved, but moving
  another item or inserting before it cleared document focus while the retained
  input's own selection range remained observable.
- **Evidence:** E3; corrected direct-input observations in `scripts/test.mjs`.
- **Impact / workaround:** Medium for rich editing; no manual restoration was
  added; document tested-browser behavior only.
- **Recommended action:** Cross-browser interaction study; complexity Medium;
  M4.5.4 follow-up/later consumer milestone.

### DX-010 — Compiler closure diagnostics

- **Category / examples:** Compiler authoring; Conditional and keyed markers.
- **Expected:** Closure parameter shadowing is diagnosed precisely.
- **Actual:** Unsupported dynamic JSX receives `implicit_dynamic_binding`
  diagnostics at source locations; callback naming discipline is required.
- **Evidence:** E2; `scripts/audit-negative.mjs`.
- **Impact / workaround:** Low/Medium; use explicit markers and non-shadowing
  callback names.
- **Recommended action:** Improve diagnostic explanations; complexity Low;
  compiler milestone.

### DX-011 — Query-gated test instrumentation

- **Category / examples:** Deployment hygiene; all pages.
- **Expected:** Production pages expose only application behavior.
- **Actual:** `?test=1` exposes browser verification hooks and `?benchmark`
  exposes a mount timing marker.
- **Evidence:** E1/E3; `scripts/test.mjs`, `src/bootstrap/mount.ts`.
- **Impact / workaround:** Low for local work, but requires isolation before a
  public demo; deployment was not performed.
- **Recommended action:** Build-time test entry or compile-time stripping;
  complexity Low/Medium; deployment-preparation milestone.

### DX-012 — Alpha.0 nested structural identity failure (resolved)

- **Category / examples:** Historical correctness defect; Conditional.
- **Expected:** Independent regions may reuse template-local IDs.
- **Actual:** Alpha.0 treated local IDs as globally unique and failed nested
  activation.
- **Evidence:** E3 historical failure and alpha.1 installed regression.
- **Impact / workaround:** Historical blocker, resolved; no consumer workaround
  was used.
- **Constraint:** Owner-scoped identity is now part of alpha.1 behavior.
- **Recommended action:** Keep the installed-package regression permanently;
  complexity Low; release validation.

## Priority matrix and handoff

| Priority | Findings | Reason |
| --- | --- | --- |
| Correctness protection | DX-002, DX-012 | Protect snapshot semantics and nested identity. |
| M5 research | DX-001, DX-002 | Directly affects scheduling design and completion semantics. |
| Tooling ergonomics | DX-005, DX-006, DX-007 | Reduces consumer setup friction without changing runtime semantics. |
| Later architecture | DX-003, DX-004, DX-008 | Collection/local-state/lifecycle APIs need separate approval. |
| Browser/deployment | DX-009, DX-011 | Requires environment-specific or release-process decisions. |

The next milestone should begin with an execution contract and scheduler
correctness tests, not with implicit tracking or a component rerender model.
